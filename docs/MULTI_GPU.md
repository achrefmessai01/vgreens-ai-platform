# Multi-GPU training — behaviour, requirements and verification

## TL;DR
Requesting **2 GPUs** makes the platform reserve both devices and expose them to the
container (`--gpus "device=0,1"`, `GPU_COUNT=2`). Both GPUs are only *used* if the
**training code runs a distributed strategy** (PyTorch DDP / `torchrun`). Models
generated by `vgreens-ai model onboard` now do this **automatically**; a hand-written
single-process image will see 2 GPUs but use only `cuda:0`.

## Why "2 GPUs but only 1 used" happened
The whole GPU-count path was correct end to end:

- CLI `job train --gpu-count 2` / web Submit → API validates `gpu_count ∈ {1,2}`
  (admin-gated for 2), stores it in `jobs.gpu_count`, and puts it in the RabbitMQ payload.
- Worker (`worker/worker.py`) reserves **both** GPU locks `[0,1]`, sets `GPU_COUNT=2`,
  and passes `gpu_ids=[0,1]`.
- Runner (`worker/runner.py`) builds `docker run --gpus "device=0,1"`.

The gap was the **generated training script**: `train.py` called `model.train(...)`
in a single process and never launched DDP, so PyTorch used only GPU 0.

## The fix (in `cli/vgreens_ai/modelgen.py`)
1. **Entrypoint** (`entrypoint.py`): for a **training** job with `GPU_COUNT > 1`, it
   relaunches training under `torchrun`:
   ```
   python -m torch.distributed.run --standalone --nproc_per_node=$GPU_COUNT /app/train.py
   ```
   Single-GPU and processing jobs run in-process, unchanged. If `torchrun` can't start,
   it falls back to a single process (single-GPU) instead of failing.
2. **`train.py` is rank-aware**: it reads `RANK`/`WORLD_SIZE`; only rank 0 stages
   `/data` (others wait on a sentinel), and only rank 0 writes the checkpoint, metrics,
   report and copies `/out`. All ranks train together via DDP.

Result: an onboarded model requested with 2 GPUs trains across **both** GPUs.

### Custom images
If you build your own image (not via `model onboard`), your training code must start
its own multi-process training (torchrun / DDP / framework strategy). Otherwise a
2-GPU request will still only use 1 GPU. The CLI and web app now warn about this.

## Verify on the GPU host (`gpu-worker-01`)
```bash
nvidia-smi                 # host sees the GPUs
nvidia-smi -L              # lists each GPU
# GPU visible inside a container via the NVIDIA runtime:
docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
# exactly the two devices a 2-GPU job would get:
docker run --rm --gpus '"device=0,1"' nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
```

Inside a training container (both should be visible when 2 are requested):
```bash
python -c "import torch; print(torch.cuda.device_count()); \
print([torch.cuda.get_device_name(i) for i in range(torch.cuda.device_count())])"
# expected with 2 GPUs exposed: 2
```

While a 2-GPU job runs, `nvidia-smi` (or the Monitoring page) should show **both**
GPUs with non-zero utilisation.

## Safety / scheduling
- A 2-GPU job acquires **both** GPU locks before running; two jobs never share a GPU.
- If both GPUs are not free, the job stays **queued/waiting** (re-queued), it is not
  run on one GPU and not failed just for waiting.
- 2-GPU training is **admin-only** and prompts for confirmation (it uses the whole host).
